01 — The economicsThe standard case

The case for going multichain, as usually told

01

Addressable users

Every chain you support is a user base that doesn’t have to bridge before trying you. Bridging is the highest-drop-off step in all of crypto UX.

02

Unified liquidity

One deep pool beats six shallow ones. Less slippage attracts bigger flow, which deepens the pool. It compounds.

03

Capital efficiency

LPs stop having to pick a chain. Idle capital sitting on the wrong one earns nothing for anybody.

04

Survivorship

Chain-specific incentives dry up. Living on one chain makes your position a bet on that chain’s emissions schedule.

Every one of these is repeated constantly. Only some of them survive the data — next three slides.

01 — The economicsThe resolution

Deploy few. Read many.

Deploying to a chain
Expensive & permanent
Contracts, bridged liquidity, an audit, an on-call rotation — and attack surface you own forever.
Consolidate
Be deliberate. Pick the chain where the liquidity actually is. Fewer really is safer.
Reading from a chain
Cheap & reversible
A balance query holds no funds, signs nothing, and cannot be drained.
Spread
Twenty chains of reads add zero smart-contract risk. Follow liquidity instead of predicting it.

02 — The codeBy hand

One balance. Five chains. Written by hand.

// 1. A client per chain. Each needs its own RPC URL,
//    its own key, its own rate limit, its own bill.
import { createPublicClient, http, erc20Abi,
         formatUnits } from 'viem'
import { mainnet, arbitrum, base, optimism,
         polygon } from 'viem/chains'

const clients = {
  ethereum: createPublicClient({ chain: mainnet,
    transport: http(process.env.ETH_RPC!) }),
  arbitrum: createPublicClient({ chain: arbitrum,
    transport: http(process.env.ARB_RPC!) }),
  base: createPublicClient({ chain: base,
    transport: http(process.env.BASE_RPC!) }),
  optimism: createPublicClient({ chain: optimism,
    transport: http(process.env.OP_RPC!) }),
  polygon: createPublicClient({ chain: polygon,
    transport: http(process.env.POLY_RPC!) }),
}

// 2. The same token has a different address on every
//    chain. Maintained by hand. Goes stale silently.
const USDC = {
  ethereum: '0xA0b8...eB48',
  arbitrum: '0xaf88...6831',
  base:     '0x8335...2913',
  optimism: '0x0b2C...5Ff85',
  polygon:  '0x3c49...3359',
} as const

// 3. Decimals differ per chain for some tokens.
//    Assume nothing.
const DECIMALS = { ethereum: 6, arbitrum: 6, base: 6,
                   optimism: 6, polygon: 6 }

// 4. Your own retry logic, because free-tier RPCs
//    fail, and nobody ships without this after the
//    first 2am page.
async function withRetry<T>(
  fn: () => Promise<T>, tries = 3
): Promise<T> {
  for (let i = 0; i < tries; i++) {
    try { return await fn() }
    catch (err) {
      if (i === tries - 1) throw err
      const ms = 2 ** i * 250
      await new Promise(r => setTimeout(r, ms))
    }
  }
  throw new Error('unreachable')
}

// 5. Finally, the thing you actually wanted.
export async function getUsdcBalances(
  wallet: `0x${string}`
) {
  const jobs = Object.entries(clients).map(
    async ([chain, client]) => {
      const raw = await withRetry(() =>
        client.readContract({
          address: USDC[chain as keyof typeof USDC],
          abi: erc20Abi,
          functionName: 'balanceOf',
          args: [wallet],
        })
      )
      return [chain, formatUnits(raw,
        DECIMALS[chain as keyof typeof DECIMALS])]
    }
  )
  return Object.fromEntries(await Promise.all(jobs))
}
~50 lines 5 RPC keys, bills, rate limits 2 hand-maintained tables 0 failover
02 — The codeThe turn

Now ask what an agent asks

“What do I hold?”
eth_getTokenBalances — the method does not exist. A node stores state by address; it cannot enumerate what you own.
“What is it worth?”
Not on-chain in any readable form. Price is off-chain data by nature.
“Where is the carry?”
Hyperliquid funding and tick premium aren’t on an EVM chain you can eth_call.
“Balance of USDC?”
Raw RPC, 140ms, 5/5 chains — and it beat the aggregator, which took 5.4s and got 4/5. The honest comparison.

The first three aren’t slow through RPC. They are impossible. That’s the argument — not keystrokes.

Now add one more chain.

// src/config.js - the entire cost of chain #6, in theory
export const CHAIN_IDS = {
  ethereum: 1,  optimism: 10,  polygon: 137,
  base: 8453,   arbitrum: 42161,

One line, five seconds — and the agent still cannot answer a single question about Conflux, because nothing routes it. So the chain comes back to you: an endpoint, the eSpace token address, its decimals, normalization, a health check. Forty lines, for chain number six.

You just watched the abstraction disappear. That gap is the measurement.

03 — The artifactTonight’s open issue

So what does adding a chain actually take?

Endpoints
Reliable RPC access, with at least one fallback provider
Token registry
Canonical addresses, symbols and decimals, per chain
Normalization
Mapping provider responses into the unified schema
Health & failover
Checks, thresholds, and what “this provider is down” means
Archive access
Historical state, if you want more than the latest block
Test vectors
Known wallets, known balances, known edge cases
